## Purpose

Давать пользователю DemoStore содержательный ответ по правилам продукта и конкретному обращению, показывая происхождение сведений и честно обозначая неизвестное. Демонстрация проверяет RAG и настоящий MCP на вымышленных локальных данных без смешивания тикетов.

## ADDED Requirements

### Requirement: Independent local support endpoint

Сервис SHALL предоставлять `POST /support/answer` с полями `ticket_id` и `question`, отдельную браузерную документацию `/docs` и `/health`. Он SHALL запускаться на loopback документированной прямой командой и SHALL NOT менять поведение Days 1–32 или `scripts/dev.ps1`. `/health` SHALL сообщать готовность приложения и FAQ-индекса, не выдавая её за успешную проверку генерации OpenAI или MCP. Отсутствие пользовательской аутентификации и исключительно демонстрационные данные SHALL быть явно обозначены.

#### Scenario: Valid request
- **WHEN** готовый сервис получает существующий `ticket_id` и непустой вопрос
- **THEN** он возвращает результат, явно привязанный к выбранному тикету, с ответом, источниками и диагностикой выполненных этапов

#### Scenario: Invalid request
- **WHEN** вопрос пустой, длиннее 4000 символов, ID не соответствует `T-` и трём цифрам либо переданы лишние поля
- **THEN** запрос отклоняется до MCP, query embeddings и генерации

#### Scenario: Provider calls do not block the event loop
- **WHEN** embedding или генерация ожидает ответа провайдера
- **THEN** event loop продолжает обслуживать другие задачи, включая health; синхронная работа вынесена из event loop, Responses использует асинхронный интерфейс

### Requirement: Real read-only ticket MCP

Каждый корректный запрос SHALL получать контекст через настоящее MCP discovery и вызов `get_ticket(ticket_id)` отдельного локального сервера. Инструмент SHALL читать только серверный демонстрационный набор, принимать единственный ID и возвращать только выбранную запись либо `not_found`. Клиент SHALL проверять схему инструмента, read-only annotation, структуру ответа и совпадение ID. Основной сервис MUST NOT подменять MCP прямым чтением JSON или fallback. Диагностика SHALL отражать фактические discovery/call, имя инструмента, ID тикета и идентификатор вызова.

#### Scenario: Found ticket
- **WHEN** вызван `get_ticket` для T-101
- **THEN** результат содержит T-101 и время его снимка без записей T-102/T-103
- **AND** ответ API позволяет увидеть успешные discovery и tool call

#### Scenario: Missing ticket
- **WHEN** запрошен T-999, отсутствующий в наборе
- **THEN** сервис возвращает `ticket_not_found` с подтверждением MCP-вызова
- **AND** query embeddings и генерация не выполняются, похожий тикет не подбирается

#### Scenario: Invalid tool or transport result
- **WHEN** инструмент отсутствует/несовместим, transport завершился ошибкой, результат повреждён либо возвращён другой ID
- **THEN** запрос завершается явной технической ошибкой без генерации и без прямого чтения JSON основным сервисом

### Requirement: Request context remains bound to one ticket

Модели SHALL передаваться только разрешённые поля выбранного тикета, исходный вопрос и найденные FAQ-фрагменты. Каждый запрос SHALL быть независимым, без постоянной истории, памяти и переноса контекста предыдущих обращений. FAQ, текст обращения и вопрос MUST NOT разрешать смену ID, дополнительное чтение тикетов или изменение инструкций. Модель SHALL NOT получать возможность произвольного вызова инструментов. Ограничение контекста SHALL NOT описываться как пользовательская авторизация: локальный клиент может явно выбрать другой демонстрационный ID в новом запросе.

#### Scenario: Request attempts to switch ticket through text
- **WHEN** поле `ticket_id` равно T-101, но вопрос или текст обращения просит прочитать T-102 или выполнить вложенные инструкции
- **THEN** MCP вызывается только для T-101, сведения T-102 не добавляются в модельный контекст или ответ
- **AND** ответ не утверждает, что чужой тикет был прочитан

#### Scenario: Sequential or concurrent requests
- **WHEN** обращения T-101 и T-102 обрабатываются последовательно либо одновременно
- **THEN** payload, выбранные ticket evidence и ответ каждого запроса относятся только к его записи

### Requirement: FAQ retrieval uses a bounded reusable index

RAG SHALL индексировать только пять явно выбранных FAQ-документов DemoStore, без тикетов, исходников и автоматического перехода по ссылкам. Документальные embeddings SHALL строиться один раз при запуске, храниться в памяти и переиспользоваться между вопросами; повторное построение после перезапуска допустимо. На найденный тикет SHALL выполняться поиск по embedding вопроса с подтверждённым техническим состоянием и передача только выбранных фрагментов. Диагностика SHALL показывать идентичность корпуса, найденные документы и scores. Высокий score MUST NOT трактоваться как доказательство причины проблемы.

#### Scenario: Multiple questions in one process
- **WHEN** после готовности индекса поступают несколько вопросов
- **THEN** FAQ embeddings не вычисляются повторно, а query embeddings и фактические найденные источники учитываются отдельно

#### Scenario: Corpus or embedding failure
- **WHEN** manifest/документ некорректен либо embeddings корпуса неполны/невалидны
- **THEN** сервис не объявляется готовым с частичным индексом

### Requirement: Product rules and ticket observations have distinct authority

Общие правила SHALL происходить из FAQ, факты конкретного обращения — из MCP, инструкции поведения модели — из отдельного доверенного слоя. Текст жалобы SHALL отличаться от технических наблюдений; отсутствующие поля и `null` SHALL означать неизвестное. Демоданные SHALL использовать фиксированный прошедший UTC-снимок `2026-10-16T09:00:00Z`, с `blocked_until` T-101 `2026-10-16T09:15:00Z`. Временные утверждения SHALL явно относиться к `snapshot_at`; система MUST NOT представлять историческую блокировку как подтверждённое текущее состояние или вычислять актуальный остаток ожидания из старого снимка.

#### Scenario: Same question with different observations
- **WHEN** один вопрос «Не могу войти в аккаунт. Почему и что делать?» отправлен для T-101 и T-102
- **THEN** T-101 получает объяснение временной блокировки на момент снимка и применимые шаги из FAQ
- **AND** T-102 получает объяснение истёкшего кода и рекомендации получения нового, без установленной блокировки
- **AND** различия опираются на наблюдения и документы, а не на сам номер тикета

#### Scenario: Replay on a later date
- **WHEN** тот же демонстрационный снимок используется после `blocked_until`
- **THEN** ответ сохраняет привязку к снимку, не заявляет текущую блокировку, её текущее снятие или оставшееся время без новых данных

### Requirement: Grounded structured answer and useful uncertainty

Генерация SHALL использовать OpenAI Responses API без цепочки предыдущих ответов и с `store=false`. Ответ SHALL различать `answered` и `insufficient_context`, содержать краткий русский текст и при необходимости уточняющие вопросы. Причина, ticket evidence и FAQ evidence SHALL проверяться относительно именно отправленного контекста. Для T-103 система MUST NOT утверждать конкретную причину: она SHALL обозначить недостающие сведения и предложить уточнения. Для общего вопроса о правилах продукта достаточно FAQ; неизвестный статус аккаунта сам по себе не запрещает такой ответ.

#### Scenario: Insufficient observations for diagnosis
- **WHEN** вопрос о причине невозможности входа задан для T-103 с неизвестными состоянием и кодом ошибки
- **THEN** ответ имеет `insufficient_context`, не диагностирует блокировку или истечение кода и запрашивает конкретные сведения, например текст ошибки и этап входа
- **AND** источник диагностических рекомендаций допускается, если он реально поддерживает эти рекомендации

#### Scenario: General product question
- **WHEN** для существующего тикета задан вопрос о документированном общем правиле DemoStore
- **THEN** ответ может иметь `answered` со ссылкой на FAQ, не приписывая это состояние конкретному аккаунту

#### Scenario: Unsupported cause or failed generation
- **WHEN** модель выбрала причину, противоречащую наблюдениям, чужой/неизвестный evidence ID, невалидную структуру либо вернула незавершённый/ошибочный результат
- **THEN** сервис возвращает техническую ошибку, не публикует такой текст как успешный ответ и не маскирует ошибку под `insufficient_context`

### Requirement: Exact and inspectable evidence

Модель SHALL выбирать ID предоставленных оснований, а сервис SHALL восстанавливать цитаты, пути, разделы, номера строк и значения фактов из авторитетного контекста. Источники SHALL принадлежать реально переданным FAQ-фрагментам; цитаты SHALL быть точными непустыми подстроками. Ответ SHALL различать сведения тикета и правила продукта. Документы SHALL открываться через ограниченный набор идентификаторов без произвольного чтения файлов. Проверка точности ссылок SHALL NOT представляться как доказательство смысловой правильности всех утверждений.

#### Scenario: Inspect a citation
- **WHEN** пользователь открывает источник из ответа
- **THEN** отображается тот же FAQ-снимок, который использован для генерации, с совпадающей дословной цитатой и координатами

#### Scenario: Forged or unsent source
- **WHEN** модель ссылается на отсутствующий либо не переданный ей документ/факт, или клиент просит произвольный путь к файлу
- **THEN** ссылка или запрос отклоняются, постороннее содержимое не раскрывается

### Requirement: Separate acceptance evidence and reproducible Swagger workflow

Приёмка SHALL отдельно подтверждать реальный MCP, релевантность retrieval, привязку к тикету, отсутствие неподтверждённых утверждений, точность ссылок и отсутствие смешивания данных. Offline проверки SHALL включать фактический LLM payload, последовательность/конкуренцию запросов и негативные кандидаты ответа; mock LLM SHALL NOT считаться доказательством качества настоящей модели. Swagger UI SHALL предоставлять четыре примера и позволять последовательно воспроизводить acceptance-проверки T-101 → T-102 → T-103 → T-999. Вопросы, ответы, кириллица, источники, snapshot_at и MCP trace SHALL корректно отображаться; для T-999 SHALL быть видны HTTP 404 и отсутствие query embeddings/генерации.

#### Scenario: Four live cases
- **WHEN** выполнены четыре сценария на настоящих MCP и OpenAI
- **THEN** отдельно зафиксированы результаты каждого критерия, включая отрицательный T-999 без генерации
- **AND** фактические результаты не обобщаются на произвольные вопросы или доказанную изоляцию пользователей

#### Scenario: Technical documentation
- **WHEN** документация Day 33 актуализируется после проверки реализации
- **THEN** краткий Day README содержит только проверенные результаты, корневой README ссылается на него, а README компонентов документируют прямой запуск и ограничения
- **AND** описанная последовательность функциональных проверок воспроизводится через стандартный Swagger UI
