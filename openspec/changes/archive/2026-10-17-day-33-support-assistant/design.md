## Context

Мотивация и границы — в [proposal.md](proposal.md), поведение — в [spec](specs/ticket-support-assistant/spec.md). Days 21–24 уже предоставляют загрузку Markdown, embeddings, cosine search и проверку цитат; Day 31 — рабочий stdio MCP и выбор evidence ID. Общий `app.main` запускает хранилища прежних дней, поэтому Day 33 использует самостоятельный app в том же backend-окружении.

Design нужен: изменение связывает HTTP, локальный MCP-процесс, retrieval и LLM, а также определяет границы данных и проверяемость результата. Существующие `gpt-5.6`, Responses-адаптер, `text-embedding-3-small`/1536 и MCP SDK 2.2.0 сохраняются. Установка новых инфраструктурных зависимостей не планируется.

## Goals / Non-Goals

**Goals:** один ограниченный запрос с явными стадиями, воспроизводимый демонстрационный снимок, краткий ответ с проверяемыми основаниями, небольшой набор содержательных проверок.

**Non-Goals:** свободный agent loop, tool choice со стороны LLM, действия над аккаунтом, отдельная CRM/таблица пользователей, аутентификация, постоянная память, дисковый векторный индекс, streaming UI, Android, развёртывание вне loopback. Не менять общие контракты и `scripts/dev.ps1`; не переносить порог 0.50 и frozen runs прежних экспериментов.

## Decisions

### 1. Самостоятельный app и прямой запуск

Размещение: `backend/app/support_assistant/` с небольшими модулями `api.py`, `models.py`, `service.py`, `rag.py`, `mcp_client.py`, `ticket_mcp_server.py`; launcher `backend/scripts/day33_ticket_mcp.py`. Данные — в `day-33-support-assistant/`. Это изолирует lifecycle и не требует регистрации router в `app.main` или универсализации Day 31.

Планируемая команда из корня репозитория в PowerShell 7 (после реализации):

```powershell
& .\backend\.venv\Scripts\python.exe -X utf8 -m uvicorn app.support_assistant.api:app --app-dir backend --host 127.0.0.1 --port 8033 --env-file backend/.env
```

При `OPENAI_API_KEY` в окружении `--env-file backend/.env` можно опустить. Ключ не передаётся в аргументах. Один worker, без `--reload`; процесс остаётся в управляемой терминальной сессии с stdout/stderr. Готовность отдельного app проверяется HTTP GET `http://127.0.0.1:8033/health`, а не `dev.ps1 status`, который относится к старому backend. Исключение прямого запуска для Day 33 явно одобрено пользователем.

`/docs` содержит примеры четырёх запросов и пометку «DemoStore: вымышленные данные, без пользовательской аутентификации». `/health` сообщает готовность FAQ snapshot и его fingerprint, не запускает тестовый MCP/LLM. Lifespan строит FAQ-индекс до готовности и закрывает OpenAI-клиенты при остановке. Ошибка построения останавливает запуск с безопасным сообщением.

Альтернатива router в общем app отвергнута из-за несвязанных хранилищ/lifecycle. Дополнительный профиль `dev.ps1` исключён по решению пользователя.

### 2. Данные и время снимка

`corpus.json` содержит явные записи `source`/`source_type=documentation` для пяти Markdown-файлов в `day-33-support-assistant/faq/`: `login.md`, `temporary-lock.md`, `expired-code.md`, `login-diagnostics.md`, `delivery.md`. Manifest использует пути относительно корня репозитория. Каждая статья короткая, самостоятельная, с условиями применения и действиями. Отдельные документы позволяют существующему chunker делать содержательный выбор; единый короткий FAQ мог бы стать одним chunk.

Вымышленные правила: пять неудачных попыток вызывают временную блокировку на 15 минут; код подтверждения действует 10 минут, истёкший код нужно заменить новым. FAQ описывает правила, а не состояние конкретного пользователя. Статья диагностики перечисляет нужные уточнения; доставка служит нерелевантным контрольным документом.

`tickets.json` имеет `{schema_version: 1, snapshot_at, tickets: [...]}`. Каждая запись: `{ticket_id, message, observations}`; структурированные observations содержат только необходимые поля:

| Тикет | account_status | error_code | Дополнительные наблюдения |
|---|---|---|---|
| T-101 | temporarily_locked | AUTH_TEMP_LOCK | failed_attempts=5, blocked_until |
| T-102 | active | VERIFICATION_CODE_EXPIRED | verification_status=expired |
| T-103 | null | null | дополнительных подтверждённых наблюдений нет |

Одинаковый `message`: «Не могу войти в аккаунт». Заведомо прошедший фиксированный снимок: `2026-10-16T09:00:00Z`, `blocked_until` T-101: `2026-10-16T09:15:00Z`. Все datetime с timezone, отображение с явной зоной. Дубли ID и некорректный снимок отклоняются сервером. Реальные имена, email, пароли и значения кодов отсутствуют.

MCP возвращает время снимка вместе с выбранным тикетом. Ответ о блокировке говорит «на момент снимка»; сервер показывает исходные временные поля. Модель не вычисляет оставшееся ожидание от системных часов и не утверждает, что сейчас блокировка продолжается или снята. Статические fixtures выбраны вместо обновляемых часов ради повторяемости acceptance-проверок и тестов.

### 3. Настоящий MCP с единственным разрешённым чтением

Узкий клиент создаёт stdio server subprocess тем же Python, выполняет initialize через SDK, paginated `list_tools` и один `call_tool('get_ticket', {'ticket_id': ...})`. Клиент проверяет имя, обязательный строковый ID, запрет дополнительных аргументов, output schema и read-only annotation. Общий deadline MCP — 15 секунд; async context закрывает соединение и дочерний процесс при успехе, ошибке и отмене. Секреты OpenAI не включаются в среду сервера; stdout предназначен только MCP.

Новый сервер использует шаблон `developer_assistant/git_mcp_server.py`, но без Git и без изменения старого инструмента. Путь tickets.json фиксирован сервером, не принимается от HTTP/LLM. Только этот сервер читает набор; результат `{status: found|not_found, ticket_id, snapshot_at, ticket|null, call_id, server_pid}` валидируется на границе клиента, включая согласованность status/ticket и запрошенного ID. Подробности JSON/локальные пути не попадают в ошибки API.

Компактный trace строится по фактическим результатам SDK: protocol, server, discovery, tool, requested_ticket_id, call, call_id. Коррелированное stderr-событие сервера допустимо как дополнительное evidence, но не условие успеха протокола. Неизвестный тикет возвращается штатно; сбой MCP прекращает запрос без provider fallback. Удалённый MCP Weeks 4 и передача tools в Responses не нужны: backend явно получает единственный необходимый контекст.

### 4. RAG один раз на процесс

Без изменения контрактов переиспользуются `document_indexing.corpus.load_corpus/Source`, `chunking.chunk_source`, `embedding.OpenAIEmbedder`, `first_rag.core.Index/vector_norm/search`. Не используются старые `read_index`, pinned baseline, SQLite и специфичный retrieval Day 31 с добавлением введения документа.

На старте: загрузить allowlist, сформировать chunks и fingerprint нормализованного корпуса/настроек, одним batch для небольшого корпуса вычислить и проверить embeddings. Полный успешный snapshot сохраняется в памяти app и больше не мутируется. Документы меняются только через перезапуск; просмотр источника использует этот же snapshot, а не повторно читает изменённый файл.

На запрос после успешного MCP: один embedding строки из исходного вопроса и известных `error_code/account_status/verification_status`, затем cosine top-2 (`min(2, chunk_count)`). Не включать в embedding ID, полный тикет и свободный текст жалобы. Выбранные тексты плюс техническое состояние позволяют различить случаи; причина всё равно определяется наблюдениями, а не score. Rewrite, reranker и непроверенный score threshold исключены. Если неизвестен код, не подставлять предполагаемое состояние.

Trace показывает fingerprint, doc/chunk IDs, ranks/scores, отдельно startup corpus embeddings и query embedding_calls. Создание синхронного embedder, embedding HTTP-вызов и закрытие клиента выполняются внутри `asyncio.to_thread`; Responses использует существующий асинхронный `OpenAIResponsesLlmClient`/`AsyncOpenAI`. Проверка heartbeat event loop покрывает обе стадии без изменения общих клиентов. Повторный запуск может заново индексировать пять статей; это осознанный компромисс вместо дискового кэша.

### 5. Формирование и проверка ответа

```text
request --> validate input --> MCP discovery/call --> validate one ticket
                                                       |
                                                       v
                       FAQ index <-- query embedding + confirmed state
                           |
                           v
instructions + question + ticket facts + retrieved FAQ --> Responses
                                                              |
                                                              v
                         evidence/status/cause validation --> HTTP answer
```

Один `OpenAIResponsesLlmClient.complete` с отдельным `AgentConfig` (`gpt-5.6`, reasoning none, strict JSON schema, truncation disabled, max_output_tokens=2000). Существующий адаптер даёт `store=False`, отказ/incomplete/error и usage; нет previous_response_id, conversation store, автоматического исправления или второго вызова модели.

Три отдельных блока в user payload: question, ticket_context, faq_context; правила находятся в instructions. Ticket message помечен как сообщение пользователя, observations — как технические сведения. Никакие вложенные инструкции в данных не расширяют полномочия. FAQ index допускает совместное использование, но context/result/evidence map каждого запроса создаются отдельно.

Модель возвращает `{status, answer, cause, faq_evidence_ids, ticket_fact_ids, clarifying_questions}`. Все поля обязательны, extra fields запрещены. `cause`: `temporary_lock|expired_code|unknown|not_applicable`; последнее относится к общему вопросу о продукте без диагноза. Это маленький структурированный контроль, а не движок произвольных правил. Допустимость конкретной причины проверяется по observations, никогда по T-101/T-102. `unknown` для диагностического ответа требует `insufficient_context` и содержательных уточнений; неизвестное состояние не запрещает отвечать на общий FAQ-вопрос с `not_applicable`.

Переиспользовать чистые `quote_options/evidence_records` Day 31 для FAQ. Модель выбирает ограниченные FAQ evidence ID и ticket fact ID из отправленных наборов; сервис восстанавливает полные цитаты и значения. Идентичность тикета и snapshot_at HTTP-ответ берёт из проверенного MCP-результата, не из модели. Для конкретного диагноза необходимы подтверждающие ticket facts и FAQ evidence; для answered по общему правилу — FAQ evidence. `insufficient_context` может содержать релевантную цитату из диагностики; пустые sources допустимы при отсутствии документального основания, без декоративных ссылок. Проверяются membership, дубли, непустые поля, совместимость status/cause и наличие оснований.

Детерминированные проверки не доказывают соответствие каждой фразы её ссылке. Противоречие свободного текста структурированной причине и смысловая поддержка цитат проверяются отдельно в live-рубрике; не обещать универсальный semantic validator. При известном ID другого тикета в вопросе не выполнять никаких дополнительных чтений; результат не должен выдавать сведения о нём.

Внешний ответ: `ticket_id`, `snapshot_at`, `status`, `answer`, `cause`, `clarifying_questions`, восстановленные `ticket_facts`, `sources` с цитатами и `trace`. `GET /support/sources/{doc_id}` отдаёт нумерованный plain text из snapshot; ID разрешён только из manifest. Источник не рендерится как произвольный HTML; URL/путь не создаётся моделью.

Ошибки: 422 — вход; 404 `ticket_not_found` — успешный отрицательный MCP; 503 `mcp_unavailable` — transport/discovery/schema/result; 502 `retrieval_failed`, `generation_failed` или `answer_validation_failed` — ошибка соответствующего этапа. Категории `infrastructure`, `validation`, `semantic_error` различают технический сбой, неправильную структуру/evidence и обнаруженное противоречие причины наблюдениям (без претензии на проверку всего свободного текста). Возвращать безопасный код и trace выполненных стадий, не upstream body. Для T-999 после старта нет query embeddings или generation, хотя FAQ уже был индексирован при запуске.

### 6. Проверки и пользовательский сценарий Swagger UI

Цель — примерно 12–18 параметризованных offline/integration случаев, не квота тестов. Группы: настоящий stdio discovery/call/cleanup; отсутствие fallback; несовпадение ID и лишние аргументы; повторное использование FAQ embeddings; фактический payload; sequential/concurrent запросы; неизвестный тикет; prompt injection в question/message; поддельные evidence; кандидат с temporary_lock для активного T-102; неизвестное состояние T-103; даты снимка. Для проверки независимости от номера менять observations в fixture, сохраняя ticket_id. Fake embeddings проверяют механику, не семантическое качество поиска; fake LLM проверяет границы и валидацию, не качество настоящего ответа.

Живые четыре запроса используют одинаковый вопрос «Не могу войти в аккаунт. Почему и что делать?» и ID T-101 → T-102 → T-103 → T-999. В рубрике отдельно: реальный MCP, нужный FAQ в выдаче, соответствие фактов, отсутствие выдуманных причин/текущих состояний, точность и смысл ссылок, отсутствие чужих фактов. Если возникает ошибка, исправить её и повторить затронутый сценарий, сохранив честное описание проверки. Минимальные регрессии относятся к импортируемым общим компонентам; Android/полный UI-прогон не нужны.

Swagger UI предоставляет четыре примера запросов и позволяет последовательно выполнить T-101 → T-102 → T-103 → T-999. Проверяются корректное отображение вопросов и ответов, кириллицы, sources, snapshot_at и trace.mcp; HTTP 404 и нулевые счётчики дальнейших вызовов у T-999 должны отображаться явно. В длинном JSON используется прокрутка стандартного блока ответа. Дополнительный интерфейс не нужен.

Краткий Day README следует трём разделам AGENTS.md; корневой README получает относительную ссылку. Контракты/ограничения — backend README, команды/проверки — scripts README, подробная приёмка — OpenSpec. В planning-фазе эти документы приложения не создаются и результаты не утверждаются.

## Risks / Trade-offs

- Нет аутентификации → только loopback и вымышленные данные; любой локальный клиент может выбрать любой ID. Проверка границ запросов не доказывает разграничение пользователей.
- Точная цитата может не поддерживать вывод → отдельная содержательная live-рубрика; небольшой enum cause закрывает лишь явно моделируемые противоречия.
- Top-2 может пропустить нужную статью → оценить фактический retrieval четырёх случаев; править содержание/поисковую строку осознанно, не подставлять источник по номеру тикета.
- Снимок устаревает → явно показывать snapshot_at, проверять воспроизведение на другой дате и не рассчитывать текущий остаток блокировки.
- OpenAI недоступен, rate limit или длинный ответ → безопасная ошибка, отсутствие фоновых повторов и отдельная проверка доступа/задержек. Фактические наблюдения ограничены выполненными live-сценариями из validation.md.
- Startup embeddings повторяются после перезапуска → допустимо для пяти документов; один worker и отсутствие reload ограничивают лишние вызовы.
- Объём может выйти за 4–6 часов → не добавлять UI, дисковый кэш, rewrite, auth или обобщённый framework; сохранить время для Days 34–35.

## Migration Plan

Миграций существующих данных нет. После отдельного разрешения добавить новые файлы и документацию, выполнить целевые проверки, запустить app и пройти live-приёмку. Старый backend/Android не переключаются на новый app. Откат локального демо — остановка его управляемой сессии; общие хранилища и команды прежних дней остаются прежними. Commit/push и завершение дня требуют отдельного запроса пользователя.
