## Context

Мотивация описана в proposal.md. Backend уже использует Responses API, `gpt-5.6` и OpenAI Python SDK; общий `OpenAIResponsesLlmClient.complete()` нормализует ответ в текст и теряет function calls. Новый цикл должен сохранять native response items без изменения общего клиента.

Проверено при планировании 2026-10-17: Python 3.14.7, установленный `openai==2.54.0`, ограничение зависимостей `openai>=2,<3`. Проверка через HTTP MockTransport прошла два обмена SDK: strict function schema, разбор `function_call`, сериализация `function_call_output` с тем же `call_id`, финальный текст. Сетевых запросов не было; совместимость аккаунта и реального исполнения модели ещё НЕ подтверждена.

[Документация модели](https://developers.openai.com/api/docs/models/gpt-5.6-sol) подтверждает Responses/function calling и разрешение alias `gpt-5.6` в GPT-5.6 Sol. [Протокол](https://developers.openai.com/api/docs/guides/function-calling) описывает strict schemas и возврат tool outputs. Это основание для предварительного выбора, а не замена live-проверке.

## Goals / Non-Goals

**Goals:** один запуск решает цель по ограниченному набору исходников, создаёт один проверяемый кандидат и отделяет решение модели от полномочий программы. Повторный запуск использует те же входные байты, но не обязан повторять текст или порядок действий.

**Non-Goals:** семантический индекс всего репозитория, изменение/исполнение исходников, shell-инструмент, удаление/переименование файлов, память между задачами, многопользовательская защита, ОС-песочница и транзакции нескольких выходных файлов. Инфраструктурные исключения не расширяют доступ модели.

## Decisions

### 1. Сначала проверка протокола, затем файловая реализация

Первый шаг apply — короткий read-only smoke текущего SDK и `gpt-5.6`: native `list_files` с минимальным фиктивным результатом, возврат результата по `call_id` и финальный ответ. Начальная конфигурация: `reasoning.effort=none`, `tool_choice=auto`, `parallel_tool_calls=false`, `store=false`, `truncation=disabled`, strict schema. Достаточно двух успешных model responses. При ошибке сначала устранить конкретную несовместимость и повторить только этот probe; не реализовывать весь агент поверх неподтверждённого протокола. Probe не доказывает самостоятельность двух продуктовых сценариев.

### 2. Маленький специализированный runner

Использовать SDK напрямую в модуле Day 34: goal + instructions + четыре schemas -> response -> validated function dispatch -> function_call_output -> следующий response. Сохранять нужные `response.output` items, включая reasoning items; запросить `reasoning.encrypted_content` для корректного stateless replay. Не смешивать items с урезанной текстовой историей старого клиента.

Один общий prompt описывает возможности и границы, но не порядок инструментов. Scenario ID разрешён только подготовке входов и verifier; runner получает goal, workspace policy и лимиты. Исходники попадают в контекст только через вызванные моделью функции. Ошибки аргументов возвращаются как ограниченные категории; выбор следующего действия остаётся модели. Refusal, incomplete, provider error, повреждённая трасса и исчерпание бюджета завершают run без доступной записи. Финальный ответ без кандидата не считается успешным выполнением сценария.

Все tool schemas: `strict=true`, обязательные поля, `additionalProperties=false`; допускаемые optional значения задаются nullable. Независимая Python-проверка запрещает лишние поля, неверные типы, неизвестные функции и повторное исполнение одного `call_id`. MCP/agent framework отвергнуты: локальному CLI транспорт и дополнительный runtime не нужны.

### 3. Контролируемая копия реальных файлов

Manifest содержит ровно:
- `backend/app/first_rag/core.py`;
- `backend/app/developer_assistant/service.py`;
- `backend/app/support_assistant/rag.py`.

Trusted prepare копирует их из выбранной чистой ревизии worktree в новый `backend/.local/day34/runs/<run-id>/workspace/`, сохраняя относительные пути и исходные байты. Фиксируются revision, SHA-256 каждого файла, manifest/prompt/fixture versions; несовпадение ожидаемых входов останавливает подготовку. Существующая папка запуска не перезаписывается. Повтор строит новую копию тех же входов, не делает reset проекта.

Единственный целевой путь обоих сценариев — `docs/search.md` внутри workspace. Для A он отсутствует; для B туда копируется версионируемый `fixtures/search-outdated.md`. Metadata, candidates и trace лежат рядом с workspace, вне доступного модели списка. Подготовка не раскрывает модели исходники, ожидаемые ответы или критерии verifier. После run/записи проверяются хеши как копий исходников, так и исходных файлов выбранного worktree.

### 4. Четыре инструмента

| Инструмент | Контракт |
|---|---|
| `list_files()` | Только manifest-разрешённые файлы, относительные пути, размеры, SHA-256 и наличие/отсутствие разрешённой цели |
| `search_text(query)` | Буквальный поиск по трём исходникам и существующей цели, детерминированный порядок; path, line, текст, evidence ID и явная полнота/ограничение результата |
| `read_file(path,start_line,end_line)` | Ограниченный диапазон UTF-8, 1-based строки, SHA-256 и evidence ID; чтение отсутствующей цели возвращает явный статус |
| `stage_file(path,content,expected_hash)` | Один разрешённый Markdown; для создания expected_hash=null и обязательное отсутствие цели, для обновления — хеш ранее прочитанной цели; immutable candidate и diff, без записи цели |

Для цитирования модель вставляет evidence markers из реально полученных диапазонов. Программа проверяет ID и рендерит локальные относительные Markdown-ссылки на копии исходников с line anchors; в receipt сохраняются исходный repository path, revision, SHA-256 и диапазон. Ссылки проверяются по содержимому, а не только по существованию файла. Неизвестные/внешние ссылки не расширяют доступ, не открываются и не считаются evidence. Точность цитаты не доказывает логическую поддержку утверждения: её проверяют отдельно.

Полный текст небольшого документа выбран вместо произвольного patch-языка: unified diff вычисляется trusted кодом по старым и новым байтам. Обновление существующей цели требует предварительного чтения; сценарий B проверяет сохранность заранее выделенного полезного раздела.

### 5. Подтверждение конкретного кандидата

CLI предоставляет prepare, run, review, apply/reject и verify. `run` только готовит результат; никакой model tool не может подтвердить запись. `review` показывает полный diff, run ID, target и candidate ID. Candidate ID связывает path, base hash/отсутствие цели, новые байты, evidence и fingerprint исходников. Новая версия требует нового подтверждения.

`apply` повторно показывает этот diff и требует явного ввода candidate ID пользователем; общий `yes`, запуск run или ответ модели не являются подтверждением. Отдельное `reject` делает кандидата недоступным для apply. Неинтерактивный вызов без подтверждения прекращается без записи. Никаких новых API-запросов при review/apply/reject/verify.

Перед apply повторно проверяются candidate ID, bytes/hash, исходники, родительские каталоги и base hash/отсутствие цели. Любое расхождение даёт stale/conflict и требует новой подготовки и review. Для обновления: временный файл в том же каталоге, flush, повторная проверка и replace; для создания — создание без перезаписи существующего файла. Затем независимое чтение, сравнение байтов/SHA-256 и receipt. Повтор apply уже записанного кандидата подтверждает receipt без новой записи; после неоднозначного сбоя сначала сверить диск, не повторять замену вслепую. Нет общего rollback/transaction engine; неудачная проверка не объявляется успешной.

### 6. Границы файлов и ресурсов

Root задаёт приложение. Все пути проверяются до каждого чтения/поиска/stage/apply: allowlist, относительная canonical форма, запрет `..`, drive/UNC/device paths, ADS/двоеточий, управляющих символов, зарезервированных Windows-имён, trailing dots/spaces. Проверяются root и каждый существующий компонент через lstat: symlink/junction/reparse points и hard-linked файлы отклоняются. Разрешённый real path обязан оставаться внутри root; для новой цели отдельно проверяется родитель. Ошибки проверки закрывают доступ.

Нет чтения .env/.git, обхода ссылок Markdown, shell/network tools или записи в .py. Ключ поступает только из OPENAI_API_KEY процесса backend CLI; не копируется в workspace/trace. Файлы и tool outputs — недоверенные данные, не новые инструкции. Управляющие символы экранируются при выводе; диагностические исключения не печатают произвольные payload/секреты.

Начальные лимиты: 16 model requests, 15 tool attempts (включая отклонённые), 300 s на цикл модели, 75 s на один запрос в пределах остатка, SDK retries=0; 64 KiB на исходник, 256 KiB на весь разрешённый набор, 12 KiB на read/search результат, 16 KiB на документ. Полный diff кандидата показывается локально без обрезания; stage возвращает модели краткий receipt. Контекст вместе с schemas ограничен 32k оценочных tokens и 192 KiB сериализованного input; actual usage сохраняется отдельно. Никакой скрытой обрезки контекста: превышение останавливает run. Время ожидания человеческого review не расходует model deadline. Бюджет model/tool calls не обнуляется при ошибках.

### 7. Сценарии и доказательства

A: цель — найти определение и доступные использования `app.first_rag.core.search`, объяснить зависимости и создать `docs/search.md`. Эталон ограничен тремя файлами: определение, два импорта и два вызова; cosine ranking по убыванию и tie-break source/ordinal/chunk_id; developer retrieve запрашивает все chunks, берёт первые 8 и при необходимости добавляет вводный фрагмент; support retrieve добавляет известные observations к query и берёт до 2 chunks. Не утверждать, что это все потребители репозитория.

B: цель — обновить устаревший `docs/search.md` по тем же исходникам. Fixture ошибочно описывает ascending ranking, одинаковый top-k для потребителей и отсутствие дополнения query. Проверяются исправления, ссылки и точное сохранение полезного раздела «Область применения». Expected facts и раздел хранятся в verifier fixtures, не в prompt модели.

A должен показать настоящий `search_text` по нескольким файлам, чтение всех трёх исходников и модельный `stage_file` нового документа. B должен показать самостоятельное чтение всех трёх исходников и старого Markdown, исправление фактов и сохранение раздела «Область применения»; `read_file` без `search_text` допустим. Порядок вызовов не фиксирован. У обоих обязательны native calls/call IDs, корректные evidence/ссылки, staged candidate и diff, отдельное пользовательское подтверждение, проверенная запись и неизменность исходников. После offline-проверок: один live A и один live B; после их успеха повтор хотя бы одного на восстановленных входах. Сравниваются факты, сохранность файлов и корректность ссылок, не формулировки. Дополнительные генерации — только для исправленного дефекта/неполной проверки.

#### Уточнение критерия приёмки 2026-10-17

Исходный критерий требовал реальный поиск по нескольким файлам в обоих сценариях. В первом B и независимом повторе модель сама выбрала `list_files -> read_file x6 -> stage_file`, включая восстановление после превышения размера чтения. Все три исходника и документ прочитаны, исправления и сохранность полезного раздела подтверждены. Обязательный `search_text` для уже известной тройки файлов оказался избыточным ограничением самостоятельного выбора: он исключал достаточную последовательность действий только из-за отсутствия конкретного инструмента.

Пользователь явно согласовал уточнение: поиск обязателен для A, а для B принимается подтверждённое исследование прямым чтением. Это пересмотр критерия 4.2, а не новый эксперимент или выполнение пропущенного вызова. Исторические `search_text=NOT_OBSERVED` и `partial_review` у обоих B сохраняются. Текущий verifier продолжает консервативно отмечать отсутствие поиска; итоговая приёмка по уточнённому критерию фиксируется отдельно в validation.md.

A прошёл критерий поиска и записи; первый B прошёл уточнённый критерий исследования, исправления и записи. Повтор B подтвердил существенные факты и тот же полезный раздел, но его кандидат не применён. Его формулировка «восемь» вместо точного «до восьми» остаётся замечанием качества. Небольшая выборка, широкие диапазоны некоторых ссылок и два B-прогона не доказывают общую надёжность или буквальную воспроизводимость модели. Traces, candidates, diff, decisions и receipts не переписываются.

Trace связывает исходные API function_call/call_id, валидированные аргументы, tool result, следующий request, финальный ответ, candidate/diff, пользовательское approve/reject и disk receipt. Verifier без API отдельно выдаёт: observed calls, provenance/citations, expected facts (с ручной смысловой проверкой), write integrity и unchanged sources. Факт самостоятельности подтверждается trace, review runner без сценарной маршрутизации и offline-тестом разных допустимых последовательностей; само наличие call_id не доказывает автономность.

Плюс изменения README корня/backend/scripts и небольшой технический validation report в этом change. Ориентир — 12 новых файлов кода/тестов/данных/Day README и 3 обновлённых README, без миграций старых сервисов; evidence локальны, в Git допускаются только проверенные технические материалы без секретов.

Адаптировать path checks Day 31, evidence/renderer Days 31–33, immutable trace и usage-подход Days 19–20. Переиспользовать чистые helpers только без зависимости от запуска RAG/MCP; не извлекать общий framework и не рефакторить старые дни. При использовании прежнего Python executable явно задавать import root нового worktree; .env и окружение в worktree автоматически не появляются.

## Risks / Trade-offs

- Гонка внешнего изменения файла между проверкой и записью -> свежие хеши, отказ при конфликте, отдельная локальная папка одного пользователя; защита от конкурирующего злоумышленника вне scope.
- Prompt injection в комментарии -> недоверенный data channel, неизменяемая policy, отсутствие опасных инструментов, подтверждение diff и adversarial offline-тест; абсолютная семантическая невосприимчивость не обещается.
- Верные ссылки при неверном объяснении -> отдельная проверка существенных фактов и ручная смысловая оценка.
- Лексический поиск пропускает сложные alias/dynamic uses -> заявлять полноту только для известного ограниченного набора; не обещать универсальный Python/Kotlin resolver.
- Alias/SDK или provider behavior меняется -> ранний smoke, запись requested/resolved model и SDK; нет скрытой подмены модели или fallback.
- Запись прошла, receipt не записался -> явно неизвестный/ошибочный исход, сверка диска перед повтором; не заявлять rollback.

## Migration Plan

Изменение аддитивное: реализовать в отдельном worktree, выполнить protocol gate, затем целевые offline и live-проверки. Общий backend HTTP app и существующие дни остаются прежними. Для отката достаточно перестать запускать новый CLI; runtime-каталог не переносится в исходники автоматически. Публикация Git и архивирование OpenSpec выполняются только отдельным действием.
