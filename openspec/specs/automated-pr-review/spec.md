# Automated PR Review Specification

## Purpose

Автоматически анализировать изменения настоящего Pull Request с ограниченным контекстом документации и кода, выдавать проверяемый advisory-отчёт и обновлять его после исправлений без исполнения недоверенного кода.

## Requirements

### Requirement: Trusted automatic PR review
Система SHALL автоматически инициировать ревью при создании, обновлении коммитов и повторном открытии PR из того же репозитория в `main`. PR-trigger SHALL работать без OpenAI secret; анализ и публикация SHALL выполняться доверенной версией ревьюера из `main` после проверки происхождения события и связи с PR. Форки и Dependabot SHALL явно пропускаться до OpenAI. Отсутствующая или неоднозначная связь запуска с PR MUST NOT разрешать анализ или публикацию в угаданный PR.

#### Scenario: Open and update an eligible PR
- **WHEN** создан собственный PR в `main` либо в него отправлен новый commit
- **THEN** автоматически запускается ревью соответствующего head SHA через бесправный PR-trigger и доверенный этап
- **AND** отчёт обозначает проверенный head SHA и revision ревьюера

#### Scenario: Untrusted or unresolved trigger
- **WHEN** событие относится к форку, Dependabot, другому workflow/repository либо не позволяет однозначно подтвердить PR
- **THEN** система показывает skip или error в Summary, не вызывает OpenAI и не публикует ревью в неподтверждённый PR

### Requirement: PR content never executes with credentials
Система MUST обрабатывать diff, исходники, документацию, имена файлов и текст модели только как недоверенные данные. Код, dependencies, workflows и тесты из PR MUST NOT исполняться или импортироваться ревьюером. `OPENAI_API_KEY` SHALL быть доступен только доверенному шагу через Environment `day32-review`, ограниченный веткой `main`; ключ и GitHub token MUST NOT попадать в prompt, отчёт или logs. Публикация SHALL иметь только необходимые права и MUST NOT исправлять код, approve или merge PR.

#### Scenario: PR changes executable or instruction-like content
- **WHEN** PR изменяет Python-код, workflow, зависимости либо содержит инструкции в комментариях или названиях файлов
- **THEN** ревьюер использует собственный доверенный runtime, не выполняет содержимое PR и не интерпретирует его как команды или полномочия

#### Scenario: Environment denies a PR ref
- **WHEN** запуск из PR пытается получить Environment secret
- **THEN** политика Environment не разрешает доступ этому ref
- **AND** доверенный запуск из `main` может использовать ключ только при корректно настроенном Environment

### Requirement: Complete bounded PR snapshot
Система SHALL получать реальные metadata, список изменённых файлов, diff и необходимые версии исходников через GitHub REST API, фиксируя base/head SHA. Поддерживаемый PR SHALL укладываться в объявленные лимиты; diff MUST NOT молча обрезаться. Переименования и удалённые строки SHALL сохранять свою сторону и происхождение. При неполных, неподдерживаемых, недоступных данных или превышении лимитов система SHALL возвращать явный статус до генерации и MUST NOT объявлять PR проверенным без проблем.

#### Scenario: Stable supported diff
- **WHEN** полный текстовый diff и список файлов получены для неизменившейся пары base/head SHA и укладываются в ограничения
- **THEN** анализ использует именно этот снимок, включая различение старых и новых путей и строк

#### Scenario: Missing data or limit exceeded
- **WHEN** diff неполон, файл бинарный/запрещённый, превышен лимит либо нужный источник нельзя получить
- **THEN** выдаётся ограничение или техническая ошибка с причиной, без генерации заключения «проблем нет»

#### Scenario: PR changes while collecting inputs
- **WHEN** base/head SHA изменился во время сбора данных
- **THEN** снимок помечается stale, не смешивается с новым состоянием и не отправляется на генерацию

### Requirement: Separate bounded documentation and code retrieval
Система SHALL использовать существующий пятидокументный корпус Day 31 и ограниченный набор изменённых исходников и очевидных связанных тестов. Поиск SHALL выполняться отдельно среди документации и кода; diff SHALL передаваться модели отдельно от найденного контекста. Каждый источник SHALL сохранять path, revision, диапазон строк и идентичность фрагмента. Индекс SHALL существовать только в рамках одного PR-run; рекурсивный обход импортов и произвольных Markdown-ссылок MUST NOT выполняться.

#### Scenario: Retrieve both kinds of evidence
- **WHEN** поддерживаемый PR изменяет исходный код и доступны документация и соответствующие исходники/тесты
- **THEN** контекст содержит отдельно отобранные документальные и кодовые фрагменты с проверяемыми ссылками на их revisions
- **AND** полный разрешённый diff передан независимо от retrieval ranking

#### Scenario: Insufficient code context
- **WHEN** в поддерживаемом корпусе нет пригодных кодовых фрагментов для PR
- **THEN** система явно сообщает insufficient_context, а не выдаёт отсутствие findings за завершённое ревью

### Requirement: One structured review with validated evidence
Система SHALL выполнять не более одной Responses generation на допущенную попытку и возвращать потенциальные баги, архитектурные проблемы и рекомендации в структурированном результате. Категории SHALL допускать пустые списки. Каждое замечание SHALL иметь основание в изменении; система SHALL проверять evidence IDs, принадлежность изменённым строкам и side/revision, а Markdown, цитаты и ссылки формировать из проверенных данных. Автоматические retries, repair-generation и дополнительные LLM judges MUST NOT выполняться. Формальная проверка MUST NOT называться доказательством смысловой корректности.

#### Scenario: Valid findings or empty categories
- **WHEN** модель возвращает структурированный результат с существующими evidence IDs и допустимыми изменёнными строками
- **THEN** Python формирует отчёт по категориям, не придумывая замечаний для пустых категорий
- **AND** вывод «замечаний не найдено» ограничен проверенным SHA и доступным контекстом

#### Scenario: Invalid or incomplete model result
- **WHEN** получены неизвестные evidence IDs, неверные строки, невалидный JSON, refusal, incomplete или provider error
- **THEN** результат обозначается как ошибка/незавершённый анализ, не как успешное ревью
- **AND** повторная генерация автоматически не выполняется

### Requirement: One current advisory comment
Система SHALL публиковать один собственный обновляемый комментарий PR и краткий Actions Summary, содержащие статус, проверенный SHA, основания findings и ограничения. Она MUST NOT изменять чужие комментарии или создавать inline review comments. Публикации одного PR SHALL сериализоваться; непосредственно перед записью SHALL проверяться актуальность head SHA и пригодность PR. Устаревший запуск MUST NOT перезаписывать отчёт для более нового состояния. Отчёт SHALL оставаться привязанным к SHA, даже если PR обновился сразу после проверки.

#### Scenario: Fix commit updates the comment
- **WHEN** новый head SHA успешно проверен и PR остаётся актуальным на момент публикации
- **THEN** обновляется тот же bot comment, отображаются новый SHA и новый результат
- **AND** Summary ссылается на отчёт, не создавая отдельной обязательной системы артефактов

#### Scenario: An older run finishes late
- **WHEN** старый запуск достигает публикации после появления нового head или более нового отчёта
- **THEN** он сообщает stale/superseded в Summary и оставляет новый комментарий неизменным

#### Scenario: Review or publication fails
- **WHEN** анализ завершился технической ошибкой либо комментарий не удалось опубликовать
- **THEN** Summary показывает ошибку; для подтверждённого актуального PR доступный status comment не выдаётся за успешное ревью
- **AND** отчёт для старого SHA не представляется результатом проверки нового SHA

### Requirement: Isolated CLI and unchanged previous days
Система SHALL предоставлять самостоятельный CLI без запуска FastAPI или Android, использующий те же правила анализа, что и автоматический workflow. Локальный режим SHALL выводить отчёт без автоматической публикации. Новая функциональность MUST NOT менять контракты, исторические индексы и модельные настройки Days 1–31.

#### Scenario: Local inspection and regression
- **WHEN** CLI запущен локально или выполняются существующие целевые RAG-тесты
- **THEN** локальный отчёт не изменяет GitHub автоматически, а прежние функции и данные сохраняют своё поведение

### Requirement: Real PR demonstration and honest acceptance
Приёмка SHALL включать доверенную реализацию в `main`, отдельный PR с заранее определёнными дефектами, настоящий автоматический запуск, исправляющий commit в том же PR и повторное автоматическое обновление комментария. Основания findings и исправленный результат SHALL оцениваться вручную. Дефекты MUST NOT попадать в `main`; отсутствие findings MUST NOT интерпретироваться как доказательство отсутствия ошибок. Сохранённые выводы MUST NOT выдаваться за новый live-run.

#### Scenario: Two revisions demonstrated
- **WHEN** выполнены оба live-запуска и просмотрены findings, retrieval sources, SHA и история комментария
- **THEN** фиксируются фактические результаты обнаружения и исчезновения известных дефектов, ограничения и ссылка на PR/runs
- **AND** фактическая проверка показывает автоматизацию, а неподтверждённые технические критерии остаются незавершёнными
