# Day 07 — Сохранение контекста

## Суть эксперимента

История конкретного диалога переходит из памяти процесса в SQLite.
Алгоритм агента остаётся прежним: каждый запрос получает полную историю
успешных ходов и новое сообщение. Это сохранение контекста session;
долгосрочная семантическая память пользователя не добавляется.

После перезапуска backend история восстанавливается по тому же ID.
Отдельная карточка Android сохраняет только этот ID и восстанавливает число
ходов с сервера; предыдущие сообщения в интерфейсе не отображаются.

## Что проверяет

- Новый backend instance продолжает диалог с точным прежним контекстом.
- Успешная пара сообщений сохраняется целиком; ошибка не продвигает историю.
- «Новый диалог» удаляет историю так, что restart её не возвращает.
- После Android cold start следующий запрос содержит только новое сообщение.

## Результаты

Offline backend-тесты подтвердили восстановление из реального SQLite-файла,
точный контекст U1/A1/U2, изоляцию sessions, rollback и durable delete.
JVM-тесты подтвердили восстановление identity/count, порядок локальной записи
и сброса, обработку ошибок без автоматического replay.

Пользователь подтвердил успешную live-проверку: после полного restart backend
и force-stop Android диалог восстановился, агент ответил на вопрос о ранее
сообщённом факте. Счётчик восстановился на 1 и после продолжения вырос до 2.

Зависимости, настройка и запуск описаны в [backend](../backend/README.md)
и [Android](../android-app/README.md). `OPENAI_API_KEY` задаётся только на backend.
