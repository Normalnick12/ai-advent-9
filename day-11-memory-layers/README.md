# Day 11 — Модель памяти агента

## Суть эксперимента

Один агент использует три независимых слоя памяти: Short-term хранит разговор
текущей session, Working — состояние текущей task, Long-term — сведения владельца
памяти. Все слои durable, но имеют разный lifecycle. Записи и выбор контекста
выполняет обычный код; LLM отвечает только за generation.

## Что проверяет

- Изоляцию слоёв и явные записи в Working/Long-term.
- Сохранность inactive разговоров и задач после создания новых.
- Приоритет архитектуры текущей задачи над общей предпочтительной архитектурой.
- Различие между сохранённой памятью, выбранным model input и ответом модели.
- Восстановление identities и трёх слоёв после restart без повторных LLM calls.

## Результаты

В одном живом прогоне с OpenAI получены следующие результаты,
подтверждённые пользователем:

| Этап | Доступность / отсутствие в input | Совпадение output |
| --- | --- | --- |
| A | 5/5 | 5/5 |
| B | 5/5 | 5/5 |
| C | 5/5 | 5/5 |
| D | 5/5 | 5/5 |
| E | 5/5 | 4/5 |

На E единственный mismatch — `effective_architecture`: ожидались отсутствие
в input и `null` в output. Проверка input прошла, ответ модели не совпал.
Это model-use failure при корректном выборе контекста. Прогон ради 5/5
не повторялся; единичный результат не означает устойчивую закономерность.

После перезапуска backend и Android сохранились owner/task/session IDs,
восстановились Short-term, Working и Long-term. Для восстановления выполнялись
только scenario/current read requests, без generation, replay и provider calls.

Эксперимент показал различие: сохранённая память, выбранный контекст и ответ
модели — три отдельных результата. Корректный контекст не гарантирует точного
использования данных моделью.

Зависимости, настройка и запуск описаны в [инструкции по запуску](../scripts/README.md).
`OPENAI_API_KEY` задаётся только на backend.
