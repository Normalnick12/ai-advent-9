# AGENTS.md

## Общий подход

- Это учебный AI Advent проект, состоящий из отдельных заданий в папках `day-XX-*`.
- Размещайте каждое задание в отдельной папке `day-NN-short-name`.
- По возможности выполняйте техническую работу самостоятельно: создавайте и изменяйте файлы, устанавливайте зависимости, запускайте приложение, тесты и другие проверки.
- Не усложняйте решения без необходимости. Для учебных заданий предпочитайте минимальную и понятную реализацию.
- Используйте актуальные официальные OpenAI API и SDK, если заданием не требуется иное.
- Перед завершением проверяйте синтаксис и структуру изменённых файлов.
- Никогда не добавляйте API-ключи, токены и другие секреты непосредственно в исходный код.

## Известная проблема Windows sandbox

- Для обычных файловых операций сначала используйте стандартный механизм Codex.
- Если операция падает с известной ошибкой Windows sandbox/helper (`setup refresh had errors`, `fs sandbox helper failed` или эквивалентной диагностированной цепочкой), не повторяйте ту же sandboxed-операцию: для конкретной операции допускается максимум одна неудачная попытка стандартного механизма.
- После этой ошибки сразу переходите на одобренный `exec_command` вне sandbox. В PowerShell используйте `-LiteralPath`, перед записью проверяйте нахождение целевого пути внутри текущего workspace и изменяйте только необходимые для текущей задачи файлы.
- После fallback-изменения обязательно проверьте результат чтением файла и командами `git diff` / `git status`.
- Не используйте и не сохраняйте абсолютные пути к временным `apply_patch.bat` wrapper-файлам.
- Не тратьте время на повторную диагностику этой известной инфраструктурной проблемы во время обычной работы, если fallback работает. Она не относится к проекту или OpenSpec, а правило действует для всех файлов проекта, включая OpenSpec-файлы и обновление task checkboxes.
- Если в будущей версии Codex стандартные sandboxed Update/Delete снова начнут стабильно работать, предпочитайте стандартный механизм; fallback используйте только при фактическом появлении известной ошибки.

## Секреты и локальные файлы

Никогда не добавляйте в Git:

- `.env` и другие файлы с секретами;
- `.venv` и `venv`;
- `__pycache__` и Python-байткод;
- IDE-файлы;
- локальные кэши;
- API-ключи и токены.

Перед каждым commit проверяйте изменения на наличие секретов.

## Git workflow

Не выполняйте commit и push автоматически после каждого изменения.

Выполняйте commit и push, только когда пользователь явно просит:

- `Заверши Day XX`;
- `заверши текущее задание`;
- `commit and push`;
- или прямо просит сделать commit и push.

При завершении задания:

1. Выполните `git status`.
2. Просмотрите `git diff` и состав изменённых файлов.
3. Убедитесь, что секреты и локальные файлы не попадут в commit.
4. Запустите разумные для текущего задания проверки: тесты, линтеры и/или само приложение.
5. Если обнаружена ошибка, сначала исправьте её и повторите проверки.
6. Добавьте в Git только необходимые файлы.
7. Создайте короткий понятный commit message на английском, отражающий суть задания.
8. Выполните обычный `git push` в текущую upstream-ветку.
9. Никогда не используйте `git push --force` без явного запроса пользователя.
10. Не выполняйте `commit --amend` и не переписывайте историю без явного запроса пользователя.
11. После push снова проверьте `git status`.

В финальном отчёте укажите:

- какие проверки были выполнены;
- commit message;
- commit hash;
- ветку;
- результат push;
- чистый ли рабочий каталог.

Если commit или push невозможен из-за авторизации, sandbox, сети или прав доступа, не пытайтесь обходить безопасность. Кратко сообщите причину и команду или действие, которое требуется от пользователя.

## Запуск окружения и проверки Windows

- Используйте `scripts/dev.ps1` из PowerShell 7: `status`, `backend`, `emulator`, `unit`, `build`, `ui`. Инструкции — в `scripts/README.md`.
- Gradle запускайте через этот скрипт: он выбирает установленный JDK, сохраняет daemon/configuration cache и блокирует конкурирующие запуски через скрипт. Не запускайте одновременно сборку из Android Studio или напрямую через wrapper в том же checkout.
- Не добавляйте `--no-daemon`, `--no-configuration-cache`, `--max-workers=1`, `clean` или `--rerun-tasks` без конкретной диагностированной причины. Временный обход не становится постоянной командой.
- Если команда вернула session ID, наблюдайте за этой сессией; не запускайте вторую копию. При отсутствии прогресса читайте вывод и проверяйте владельца процесса/блокировки. Не удаляйте lock-файлы и не завершайте все Java/Python-процессы.
- Backend запускайте в отдельной управляемой терминальной сессии с доступным stdout/stderr. Готовность проверяйте через `status`; `/health` подтверждает FastAPI, не OpenAI. Перед живым сценарием отдельно проверяйте доступность backend с эмулятора.
- Разделяйте подготовку окружения, Gradle-сборку, инструментальные тесты и живой запрос API в сообщениях о прогрессе. Долгоживущий backend не должен завершаться сам по себе как обычная проверочная команда.
- Для логики запускайте соответствующие JVM-тесты; для UI — затронутый класс/метод через `ui -Test`. Текущие UI-тесты не требуют backend или OpenAI. Полный UI-прогон нужен при связанных изменениях экранов/навигации, а не после каждой правки или изменения README.
- Переиспользуйте работающий эмулятор и успешные проверки актуального кода. Повторяйте проверку только при изменении её входов/проверяемого поведения или для диагностики конкретного риска.
